2The idea in one minute

We'll go deeper in Step 1. This is just the basic picture.

An exchange receives orders: "I want to buy 100 shares of X for at most ₺50.00" or "I want to sell 50 shares for at least ₺50.10". Orders that can't trade yet wait in the order book, buyers on one side and sellers on the other, each side sorted by price.

Bids (buyers)

PriceQtyArrived
50.0010009:00:01
50.004009:00:03
49.9020009:00:02

Asks (sellers)

PriceQtyArrived
50.105009:00:02
50.2030009:00:01
50.308009:00:04

The best buyer offers 50.00 and the best seller wants 50.10, so nothing trades. The 0.10 gap between them is the spread. Now a new order arrives: SELL 120 @ 49.90. The matching engine sees that buyers will pay at least that much, so it trades:

  • 100 shares with the 09:00:01 buyer at 50.00. Same price as the next buyer, but this one arrived first. That's price-time priority.
  • The remaining 20 shares with the 09:00:03 buyer at 50.00. That buyer's leftover 20 shares stay in the book.

Your project is that engine: the program that does this matching correctly and deterministically (same input always gives the same output), measures how fast it is, compares data structures for the book, and can rebuild its state exactly after a crash.

3What your advisor approved

His reply narrows your original idea down to something you can finish in two semesters.

core

Deterministic matching engine

Price-time priority. Add, cancel, modify / cancel-replace. The order book's invariants always hold.
core · research

Data structure comparison

Order-id lookup (hash table / direct index). Price levels (balanced tree, skip list, radix tree, bitmap/array). FIFO queue per level with O(1) cancel (intrusive list). Framed as research questions; you don't have to build all of them.
core

Benchmarks & performance

Throughput; p50 / p99 / p99.9 / max latency; memory; allocation count. Different workloads: lots of cancels, aggressive market orders, narrow vs. wide price ranges.
core

Fault tolerance, part 1

Event log + snapshot + deterministic replay. After a crash, the engine rebuilds exactly the same state.
optional

Raft replication

Second phase, minimal only. He warned that full Raft could become a whole project on its own.
nice extra

Web dashboard

Read-only view of order book depth and latency. Must be a separate layer that never slows the engine. This is where your web experience helps most.
rule Nothing proprietary from your previous HFT employer: no code, no data, no internal designs. Use only synthetic or openly licensed data.

6Our step-by-step plan

We go in this order because each step feeds the next. Steps 1–6 give us everything needed for the proposal form.

1

Understand the domain from zero

  • What an exchange is; who sends orders (brokers, market makers)
  • Order types: limit, market, cancel, modify; time-in-force (IOC, FOK, GTC)
  • The order book, bid/ask, spread, depth, price levels, ticks
  • Price-time priority, partial fills, what a "trade" event looks like
  • Where the matching engine sits in a real exchange (gateway → sequencer → engine → market data)
Outcome: you can explain the problem to the jury in your own words.
2

Why it's a computer engineering problem

  • Latency vs. throughput; what p50 / p99 / p99.9 mean and why tail latency matters
  • Determinism and why replay depends on it
  • Cost of memory allocation, cache misses, branch mispredictions
  • Which data structure fits which operation (add, cancel, best price lookup)
Outcome: the "why it matters" half-page for the proposal.
3

Similar projects & research material

  • Open-source engines (e.g. liquibook, LMAX Disruptor/exchange architecture, others to evaluate)
  • Exchange protocol specs: NASDAQ ITCH / OUCH, FIX
  • Public / openly licensed market data for realistic workloads (vs. synthetic generators)
  • Books & papers on order books, data structures, event sourcing, Raft
Outcome: a reference list + the "Benzer çalışmalar" section.
4

Pick the tech stack

  • Engine language: C++ vs. Go vs. Rust
  • Build, testing, benchmarking and profiling tools
  • Dashboard stack and how it reads data without touching the critical path
Outcome: the "Yöntem ve Metodlar / tools" section.
5

Finalize scope & architecture

  • Minimum version vs. stretch goals
  • Component diagram: input → engine → event log → snapshot → dashboard
  • What our original contribution is (for the 10 originality points)
Outcome: a clear in-scope / out-of-scope list.
6

Timeline, title & the proposal form

  • Work packages week by week until December, then spring
  • Project title in Turkish and English
  • Draft the proposal form (.docx) and the submission email
Outcome: proposal sent before 1 Nov.
7

Set up the repository

  • README, CLAUDE.md, PLAN.md, ROADMAP.md with real content
