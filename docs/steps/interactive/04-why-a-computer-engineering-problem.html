Why a matching engine is a computer engineering problem

Matching orders sounds simple: put buyers and sellers together. The hard part is doing it correctly, very fast, for every single message. This page works through the first two difficulties: topic 1, the data structures behind the order book; topic 2, latency: what "fast" means and where the time goes; and topic 3, determinism: getting exactly the same result every time.

0Start here: how to read this page

No finance background is needed. This page asks one question: how should a program store the orders waiting at an exchange, so that it can react to every new message very quickly? Everything below uses the same small example. This section explains what every letter, number and block means.

1.1What the engine does, again and again

Almost every message makes the engine do one of three things:

1 · Find the best price

Lowest ask or highest bid. Needed for every incoming order, to see whether it can trade.

2 · Take the oldest order there

Price-time priority: at the best price, the order that came first trades first.

3 · Find any order by ID and remove it

Every cancel or modify. The order can be anywhere in the book, and cancels are a large share of real traffic.
Which side is "best"? For sell orders (asks) the best price is the lowest: a buyer wants the cheapest seller. For buy orders (bids) the best price is the highest: a seller wants the buyer who pays most. Each side keeps its own structure.

The lesson. Sorting makes reading fast, but any change in the middle of a contiguous array costs O(n), because everything behind it has to shift. A deque does not help: it is only fast at its two ends. Storing the sorted array in reverse (best price at the end) makes removing the best order O(1), but cancel and insert in the middle stay O(n).

Side note for topic 2: shifting is a memmove over contiguous memory, which CPUs do very fast. For a small n, an O(n) array can beat an O(log n) tree in real nanoseconds. Big-O shows how cost grows, not the actual time, which is why this project measures.

1.3Price levels: sort prices, not orders

Many orders share the same price. A busy book might hold 100,000 orders but only about 200 distinct prices. So keep a sorted container of price levels, and give each level its own first-in-first-out queue:

price 101 :  A (5)   D (3)
price 102 :  B (10)  E (4)  F (6)
price 103 :  C (2)

New order F@102

Find level 102 by binary search over the levels, O(log L). Append F to the back of its queue, O(1). A brand-new price adds a level: O(L), but over ~200 levels, not 100,000 orders.

A fully filled

Pop it from the front of the best level, O(1). When a level becomes empty, remove it.

Cancel E: still slow

With only the ID we don't know E's price, so we search every level, O(n). Then removing E from the middle of its queue shifts the orders behind it, O(k).

This is also how Liquibook behaves: its cancel goes to the price level and then walks through the orders there one by one (find_on_market).

1.4Fixing cancel: a doubly linked list and a hash map

Cancel has two separate problems, and each has a classic fix:

1 · Jump from the ID to the order

A hash map from order ID to the order: O(1) lookup on average. No searching.

2 · Remove from the middle without shifting

A doubly linked list: orders live anywhere in memory and each one remembers its neighbours, prev and next.

Try it on level 102. Removing E changes exactly two pointers, however long the list is:

Both directions are needed. In a singly linked list E doesn't know who points to it, so we would have to walk from the head again. The list still works as a FIFO queue: new orders join at the tail, trades take from the head, both O(1).

Putting them together. The hash map stores a pointer to the order's node in its list. Each order also keeps a pointer to its price level, so after unlinking it the engine can fix the level's head or tail, and remove the level if it is now empty.

1.7Two catches

The structures must stay in sync

When an order leaves the book, it must leave its list and the map. Forget one, and the map points to freed memory: a crash or a silently wrong trade. Rules like "every order in a list has exactly one map entry" are invariants. The advisor listed them as core scope, and v1's unit tests will check them. (In the live book you can see the moment between "unlink" and "erase from map": inside one operation the invariant is briefly broken, and it must hold again when the operation ends.)

Linked list nodes are scattered in memory

Following a pointer to a node that isn't in the CPU cache is slow. An array is one contiguous block; a list is not. This is where topic 2 (latency) starts, and why v3 tries intrusive lists and pre-allocated memory.

?Check yourself (topic 1)

1. Why is an unsorted array a bad order book, even though inserting is O(1)?

Finding the best price and the oldest order there needs a scan of every order, O(n), on every incoming message.

2. In a sorted array, why is cancel still O(n)?

It is sorted by price, but a cancel carries only an ID, so finding the order is a scan. Removing it from the middle then shifts the later elements.

3. Why do price levels help so much?

Many orders share a price, so the number of levels L is far smaller than the number of orders n. Sorting levels instead of orders makes the costs depend on L.

4. Why a doubly linked list and not a singly linked one?

To unlink a node in O(1) we must update the node before it. With only next pointers a node doesn't know its predecessor, so we would walk from the head.

5. What does the hash map store, and why does each order keep a pointer to its level?

A pointer to the order's node, so cancel jumps straight to it. The level pointer lets the engine fix the level's head or tail after unlinking, and remove the level if it became empty.

6. A resting order is partly filled. Does it lose its place in the line?

No. Only its quantity changes; it stays at the head with its time priority. Try it in the live book: B stays at the head after the replay.

Topic 2 of 5

Latency: what "fast" means, and where the time goes

In topic 1 we counted steps: O(1), O(n), "looked at 4, shifted 3". But the advisor, the jury and the benchmarks ask how much time something takes. This topic connects the two, and shows why they don't always agree.

2.1Latency and throughput: the single cashier

order arrives ──► [ engine works ] ──► events out
      t₀                                    t₁
               latency = t₁ − t₀

Think of a supermarket with one cashier. Latency is how long one customer takes; throughput is how many customers are served per hour. Our engine is that single cashier: one order at a time, on one thread (topic 5 explains why).

The maths. If the engine needs 2 µs per order, it can handle at most 1,000,000 ÷ 2 = 500,000 orders per second.

But a customer's real wait is their own service time plus the time spent behind others in the queue. Try it: the simulator below sends 120 orders at a steady rate, plus a burst of 10 extra orders all at once. Each bar is one order's latency.

How busy is the engine?

The lesson. An engine running close to its limit has terrible latency as soon as traffic is bursty, and real markets are bursty. A faster engine is valuable even when it is "fast enough on average", because it leaves headroom.

2.2Why an average lies: percentiles and the tail

Ten orders were measured, in µs: 2 2 3 2 2 3 2 2 2 180. The average is 200 ÷ 10 = 20 µs, yet no order took 20 µs. Nine took 2–3 µs and one took 180 µs. Sort the samples and read off positions instead:

sorted:  2  2  2  2  2  2  2  3  3  180
         └──────── 90% ────────┘     └ the slowest 10%

Now it is honest: "normally 2 µs (p50), but sometimes up to 180 µs (max)." Try it yourself: pick a preset or type your own numbers.

How a percentile is picked here: sort the samples, then take the value at position p% × N, rounded up. So p90 of 10 samples is the 9th value, and p99 of 10 samples is the 10th.

Volume

With 1,000,000 orders a day, p99 describes the slowest 10,000 orders and p99.9 the slowest 1,000. "Rare" still means thousands of real orders.

Who suffers

In a market, being slow means someone else trades first. The trader whose order lands in the tail loses that trade.

When

Slow orders tend to happen in bursts, exactly when the market is busiest (see the simulator in 2.1).

That is why the advisor asked for p50, p99, p99.9 and max instead of an average, and why the v2 benchmarks report exactly those.

2.3Where the time goes: memory

Why would one order take 180 µs when the others take 2? There are three kinds of "slow":

1 · Outside the engine

The network. Real, but not what we measure: our latency starts when the order reaches the engine, and in benchmarks the orders come straight from memory.

2 · More work

A big order that sweeps many price levels really does more trades. Expected and easy to explain; the advisor's "aggressive market orders" workload measures it.

3 · Same work, slow machine

Things you cannot see in the code. The biggest one is memory.

The CPU keeps small, fast copies of data close to itself. The bars show the rough time to read one value from each place:

L1 cache~1 ns128 KB per performance core
L2 cache~5 ns16 MB
RAM~100 ns16 GB

Sizes read from the student's Apple M2 with sysctl; times are rough typical values. An order that needs 20 memory reads takes ~20 ns if everything is in L1, and ~2 µs if everything comes from RAM. Same code, same work, 100× different.

Cache lines: why arrays win

The CPU fetches a whole cache line at a time: 128 bytes on the M2. If one order takes 32 bytes, one line holds 4 orders.

Array: orders side by side

ADBCEFGH

Reading A brings D, B and C for free, and the CPU prefetches the next line. 8 orders = 2 trips to RAM.

Linked list: nodes scattered

ADBC…

Every next may land somewhere new. 8 orders = up to 8 trips to RAM.

This is the second catch of topic 1, now with numbers. Compare cancelling one order inside a price level (the hash map has already said which level):

Level sizeSorted array (scan + shift)Doubly linked list (unlink)Likely faster

Big-O tells who wins when things get big. Only measurement tells where "big" starts. That is why the advisor's workloads include narrow vs wide price ranges: a narrow range puts many orders on each level (favours the list), a wide range puts few (may favour the array).

The rule: pay every expensive cost up front, before the market opens, when nobody is waiting. For example index.reserve(1'000'000) makes the hash map big enough once, so it never grows during trading.

A related option: if the engine gives each order a simple counter as its ID (0, 1, 2, …), the index can be a plain array where the ID is the position. No hashing, no growth, and nearby IDs sit near each other in memory. This is the advisor's "hash table vs direct index" question, measured in v3.

2.5Measuring honestly

The basic idea is simple: read a clock before and after, and keep the difference.

for each order in the workload:
    t0 = clock.now()
    engine.process(order)
    t1 = clock.now()
    histogram.record(t1 − t0)     // store it, don't print it here
report p50, p99, p99.9, max

What can make that number wrong was checked with a small throw-away C++ program on the student's Apple M2 (2026-11-25; not part of the repository):

1 · The clock is coarse

timer tick     = 41.67 ns
one clock read ≈ 18 ns

Anything shorter than a tick shows up as 0 or 42 ns. Fix: time whole operations; repeat tiny ones 1,000 times and divide.

2 · Even "nothing" has a tail

an empty region, timed 1M times
p50   = 0 ns
p99   = 42 ns
p99.9 = 83 ns
max   = 1,459 ns

The OS and hardware also need the CPU. Fix: millions of samples, percentiles, few background programs, record the machine.

3 · The first run is slow

sum 64 MB, run 1: 6,579 µs
sum 64 MB, run 2: 1,244 µs
sum 64 MB, run 3: 1,258 µs

Caches and the CPU had not settled yet. Fix: warm up before measuring.

4 · The wrong build

release (-O2):  ~1,250 µs
debug   (-O0): ~66,000 µs

A debug build was ~50× slower. Fix: always a release build, and make sure the compiler does not delete unused work (Google Benchmark's DoNotOptimize).

5 · Measuring disturbs the result

Printing each sample puts I/O on the critical path. Fix: record into an in-memory histogram (HdrHistogram); print at the end.

6 · Hiding the queue

If the next order is sent only after the previous one finished, the queue from 2.1 never shows up ("coordinated omission"). Fix: also test orders arriving on a schedule or in bursts.

7 · Different input every run

Two runs with different random orders are not comparable. Fix: a fixed seed, so every run and every version sees the same orders. This needs a deterministic engine (topic 3).

The seven rules (proposed benchmark rules for v2)

?Check yourself (topic 2)

1. An engine needs 2 µs per order on one thread. What is its maximum throughput?

1,000,000 ÷ 2 = 500,000 orders per second.

2. Why does an engine that is 100% busy behave badly during a burst?

It has no free moment to work through the extra orders, so the queue never shrinks and every later order inherits the delay. Try 100% in the simulator in 2.1.

3. Latencies 2, 2, 3, 2, 2, 3, 2, 2, 2, 180 µs: average, p50 and max?

Average 20 µs, p50 2 µs, max 180 µs. The average describes none of the orders.

4. Out of 1,000,000 orders, p99.9 = 8 µs. What does that tell you?

999,000 orders took 8 µs or less; the slowest 1,000 took longer.

5. Why can a linked list be slower than an array, even though it does fewer steps?

Its nodes are scattered, so each step can be a cache miss of about 100 ns. An array's elements share cache lines, and the CPU prefetches them.

6. How do we avoid a slow hash map growth while the engine is trading?

Reserve the full size at startup, or use a direct-index array if the engine assigns sequential IDs.

7. Why can't a single hash map lookup be timed on its own on the M2?

The timer moves in steps of 41.67 ns and reading it costs about 18 ns, while a lookup takes a few ns. Time many lookups and divide.

8. Why warm up, and why never benchmark a debug build?

The first run was 5× slower in our test, and the debug build about 50× slower than the release build. Neither says anything about the real engine.

Topic 3 of 5

Determinism: exactly the same result, every time

Topics 1 and 2 were about being fast. This one is about being exactly right, every single time. Crash recovery (topic 4), testing, and comparing v1 with v3 all rest on it.

3.1What determinism means

Think of the engine as a machine with a memory. Each input changes the state a little and produces some events:

state₀ ──(input 1)──► state₁ ──(input 2)──► state₂ ──(input 3)──► state₃ …
               │                   │                    │
            events              events               events

Determinism means every arrow is a pure rule: the next state and the events depend only on the current state and the input. Not the clock, not luck, not which CPU core ran it.

This input…

1  SELL  A  5 @ 101
2  SELL  D  3 @ 101
3  BUY   X  6 @ 102

…must always give exactly this

REST   A 5 @ 101
REST   D 3 @ 101
TRADE  X buys 5 from A at 101
TRADE  X buys 1 from D at 101
DONE   X fully filled

Today and tomorrow, on your Mac and on the advisor's PC, a thousand times in a row, down to the last byte. If one run printed the trade with D first, the engine would not be slow but wrong: A arrived first, so A must trade first.

3.2Why an exchange cares so much

1 · Crash recovery

After a crash the input log is replayed to rebuild the book (topic 4). That only works if the replay gives exactly the same book; otherwise traders' orders silently change.

2 · Testing

A test can say "this input must produce exactly these events". A non-deterministic engine fails tests at random, and a real bug can't be told apart from noise.

3 · Fair benchmarks

Comparing v1 and v3 means feeding both the same workload and checking that they make the same trades (topic 2, rule 7). Only then do the speed numbers mean anything.

4 · Debugging and auditing

"Why did my order trade at 101?" Replay the log and watch it happen again, exactly. Real exchanges and regulators rely on this.

3.3What can quietly break it

Five behaviours were discussed. Four break determinism; one is the rule itself.

Floating point, checked on your Mac

0.1 + 0.2       → 0.30000000000000004
101.1 is stored → 101.0999999999999943…
0.1 added 1000× → 99.9999999999986
100.9 + 0.2     → 101.10000000000001

The last line means a buy at 101.10 does not reach a sell computed as 100.90 + 0.20, even though both "are" 101.10. The lab below uses exactly this case.

Measuring is fine

Reading the clock to measure latency (topic 2) does not break determinism, because that number never changes what the engine does. The rule is about the engine's behaviour and outputs.

        The rule: the engine's outputs and state depend only on its input log, and nothing else. Time comes with the input, prices are integer ticks, every output comes from ordered structures, and one thread does the matching.
        

    
        3.4How to test determinism
        
    
        
      
        1 · Run twice, compare
        Same input, two runs, events written to two files, compared byte by byte or by fingerprint. Pass = identical. (This is what the lab does.)
        
      
        2 · Golden files
        Small hand-written inputs with their expected events, stored in the repository. Every change to the engine must still reproduce them exactly.
        
      
        3 · Replay check
        Run a long input and print the final book; start a fresh engine, replay the log, print again. The two must match: a rehearsal for crash recovery.
        
      
        4 · Other machines and builds
        macOS and Linux (GitHub Actions can run this automatically), debug and release builds, same fingerprints. Catches hash-order and floating-point problems.
        
      
        5 · Differential testing
        1,000,000 orders from a fixed seed through v1 and v3. Equal fingerprints prove v3 is faster and makes exactly the same trades.
        
    
        
    
        Pass means an identical event stream and an identical final book, every time, everywhere.
        

    
        ?Check yourself (topic 3)
        
    
        1. Define determinism in one sentence.
        The same inputs, in the same order, always produce exactly the same outputs and the same final state.
        
    
        2. Why can't the engine call clock.now() to timestamp trades, and what does it do instead?
        The time differs on every run, so a replay would produce different events. The time is stamped on arrival by the gateway or sequencer, recorded with the input, and the engine copies it.
        
    
        3. Why are prices stored as integer ticks?
        Floating point can't store most decimal prices exactly (100.9 + 0.2 = 101.10000000000001), so comparisons can be wrong and rounding may differ between machines. Integers are exact everywhere. Try breaker 3 in the lab.
        
    
        4. All trades are correct, but the printed book differs between macOS and Linux. Likely cause?
        The book was printed by looping over a hash map. Print from the sorted levels and FIFO lists instead. Try breaker 4 in the lab.
        
    
        5. Is reading the clock to measure latency a problem?
        No, as long as the measured value never changes what the engine does.
        
    
        6. How do we show that v3 makes exactly the same trades as v1?
        Run both on the same seeded workload and compare the fingerprints of their outputs (differential testing).
